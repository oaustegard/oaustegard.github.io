FileDrop sends a file directly between two browsers over an encrypted peer-to-peer WebRTC channel — with no signaling infrastructure at all. The connection setup normally carried by a server or a SharePoint list is instead a small code you pass to your colleague by hand, over any channel you already trust (Teams, email, a sticky note).

How it works

Copy-paste signaling

WebRTC needs each side to hand the other a few kilobytes of session-setup text (SDP) before a direct connection exists. Here that exchange is manual: the invite link carries the sender's compressed offer in its #fragment (never sent to any server, including SharePoint), and the reply link carries the receiver's answer back the same way. When the sender clicks the reply link, the newly opened tab hands the answer to the still-open invite tab over a same-origin BroadcastChannel and can then be closed — two clicks, one connection. This requires both clicks to happen in the same browser; if the invite tab cannot be found, the reply falls back to a code you paste. ICE trickle is disabled — each side waits for candidate gathering to finish so a single blob carries everything.

Phone-to-phone by QR

Because a format-2 code is only a few hundred characters, the invite and reply links fit in a scannable QR. The sender shows the invite QR; the recipient scans it with their camera app, which opens the reply page; that page shows a reply QR; the sender taps Scan reply to open an in-page camera preview (getUserMedia) and reads it, feeding the answer straight to the connection — no second tab, no BroadcastChannel. Decoding uses the browser's native BarcodeDetector where present and falls back to a bundled decoder on Safari. Laptops have cameras too; a camera-less desktop keeps the link/paste paths, which never go away.

Peer-to-peer transfer

Files stream over the resulting data channel, DTLS-encrypted, in 64 KB chunks with backpressure. Every file is SHA-256 hashed before sending and verified on arrival; a mismatch is discarded. Transfers are capped at 2 GB (assembled in memory). Incoming files must be accepted before any bytes flow.

On a phone the 2 GB cap is theoretical: mobile Safari's per-tab memory ceiling makes a few hundred MB the practical limit for a single file, since the receiver holds the whole thing in RAM before saving. The page also requests a screen wake lock while a QR is showing or a transfer is running (Safari 16.4+, Chrome, others) so the display does not sleep mid-scan or mid-transfer; if the lock is refused, just keep the screen on manually.

Trade-offs vs. the list-signaled FileDrop

No peer discovery, no rooms, one connection per page: you connect to exactly the person you exchanged codes with, which is also the security upside — the trust boundary is your IM conversation, not a shared list. The offer contains your machine's IP addresses, so only send invites to people you would tell your IP address.
